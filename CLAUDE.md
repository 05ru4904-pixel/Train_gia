## Стек и архитектура
- Python 3.11, aiogram 3.29, FastAPI, SQLAlchemy 2.0 async + asyncpg, uvicorn, Docker
- Postgres 18 на Railway. Деплой автоматический: `git push` в `main`.
- `main.py` — один процесс: FastAPI + бот пользователя + админ-бот через `asyncio.gather`.
  `RUN_ADMIN_BOT_INLINE` выносит админ-бота в отдельный сервис (`admin.py`).
- Mini App: `static/`, проверка `initData` (HMAC-SHA256, ключ `WebAppData`) на каждом
  запросе, заголовок `X-Telegram-Init-Data`.
- **Рабочая папка должна быть `Train_gia`, а не `d:\VS`** — иначе этот файл не подхватится.

## Что видит ученик (Mini App)
Четыре вкладки: **Тренажёр**, **Шпаргалки**, **Статистика**, **Профиль**.

Главная тренажёра — три входа: полный вариант (26 заданий, таймер 210 минут),
тренировка по номеру (6/9/12/15 вопросов), карточки. Плюс карточка
«продолжить», если есть незавершённая сессия.

При первом входе вместо всего этого показывается анкета, а нижние вкладки прячутся.

## Виды заданий (`core/tasks_meta.py`)
| kind | что делает ученик |
|---|---|
| `choice` | выбирает пронумерованные варианты |
| `open` | вводит слово |
| `digits` | вводит цифры, порядок не важен |
| `match` | сопоставляет А-Д ↔ 1-9, порядок важен |

**Вид определяется номером задания, а не текстом** — таблица `KIND_BY_NUMBER`:
- `open` — 1, 5, 6, 7, 25
- `choice` — 2, 3, 4, 9-14, 16, 23, 24
- `digits` — 15, 17-21, 26
- `match` — 8, 22

Без таблицы возвращаются две ловушки: у №21 материал начинается с «1) 2) 3)» и выглядит
как варианты ответа, а формулировки №12 и №16 путают даже модели.

## Как задания попадают в базу
Пользователь копирует вариант с РЕШУ ЕГЭ **как есть**, сохраняет файлом (UTF-8), шлёт
в админ-бота командой `/upload`. Бот присылает разбор файлом на вычитку и ждёт
подтверждения кнопкой. Папка `Задания/` в `.gitignore`.

Одно задание — `/add`, текстом в сообщении. Разбор тот же (`parse_one` в
`core/raw_variant.py`): вид из номера, ответ из пояснения, ID источника, дедуп,
карточка на вычитку и кнопка. Шапку можно короткую — «Задание 8» — тогда задание
считается ручным: `source_id` пустой, дубли по отпечатку. `/batch` удалён: он
разбирал задания старым шаблонным парсером и определял вид по форме сообщения.

**Главное правило парсера: при любой неоднозначности задание не собирается**, а попадает
в `problems`, и файл не пишется. Прошлый парсер разбирал текст эвристиками, на №13 молча
потерял вариант ответа и сдвинул правильные — заметили не сразу.

**Дубли ищутся по ID источника** — постоянному номеру задания на сайте («Задание 8
№ 10262»), он лежит в `tasks.source_id` рядом со своим ID. Две проверки, они про разное:
- **вариант целиком** — по одному №26. Совпал с №26 уже собранного варианта, значит этот
  вариант заливали: стоп, не создаётся ничего. Совпадение заданий №1-25 заливке **не
  мешает** — источник ставит одно и то же задание в разные варианты, это норма;
- **каждое задание** — по паре `(номер, source_id)`. Нашлось — переиспользуем с прежним
  ID, вариант просто сошлётся на него; не нашлось — создаём новое.

Отпечаток по содержимому остался запасным ключом: только для заданий без `source_id`
(набранных через `/add`). Он ломался от правки одного символа на сайте и давал копию.

## Ловушки исходников (все встречались вживую)
- **Мягкий перенос U+00AD** — по 8-9 тысяч на файл, невидим, рвёт слова внутри.
- **Латинская `A` вместо русской `А`** в столбце №22. Выглядит одинаково, столбец
  собирается из 4 позиций вместо 5, все ответы съезжают на букву.
- **Markdown-выгрузки**: шапка приходит как `↑ **Задание 2 № 45125 тип 2**`, «Пояснение.»
  как `**Пояснение.**`, часть строк дублируется подряд, пустая строка перед списком
  вариантов может пропасть, а маркер «Прочитайте текст» — потеряться совсем.
- **Источники ответа по приоритету**: `Ответ:` (все формы через «ИЛИ», «|», «;») →
  `Ответ в демоверсии:` / `Ответ редакции:` (объединяются) → `Правильный ответ:` (одна
  форма, парсер предупреждает). Ярлыки читаются только при отсутствии обычного `Ответ:`:
  под заданием бывает обсуждение, и реплика редакции подписана так же.
- **Приписки в ответе у digits**: «25; порядок не важен», «34 ИЛИ 43 в любом порядке»,
  «1234 (в любой последовательности)». Кусок без цифр раньше считался формой ответа
  и отклонял весь вариант. Теперь `split_digit_forms` берёт из ответа только цифры.
- Сайт печатает номер дважды («Задание 8 ... тип 8») — бесплатная проверка разбора.

## Соглашения, о которые легко споткнуться
- `correct` у `choice`: в JSON с единицы, в базе с нуля (`to_parsed` вычитает 1),
  на экране снова с единицы. Три системы отсчёта на одно поле.
- `correct` у `match`: везде с единицы, порядок важен — это позиции правого столбца
  в порядке букв А-Д.
- Правильный ответ не уходит на клиент, пока ученик не ответил. В полном варианте —
  до самого конца варианта, потому что до конца ответ можно менять.
- Запятая в строке ответа делит формы только если части без пробелов («145, 541»),
  иначе она часть самой фразы («не столько планы, сколько нас»).
- У `digits` запятая не делит формы вовсе: «3, 5» — это один ответ «35», а «145, 541» —
  перестановки одного набора, от них остаётся первая. Порядок цифр не проверяется
  (`evaluate_digits` сравнивает множества), поэтому обе свёртки безопасны.
- В `static/app.css` класс `.card` — это карточка-кнопка на главной. Карточка со словом
  называется `.flashcard`: имена в одном файле на всё приложение легко пересекаются.

## Анкета ученика (онбординг)
Заполняется при первом входе в Mini App и правится из профиля кнопкой «Изменить
анкету». Пока `users.onboarded_at` пуст, `/api/state` отдаёт `needs_onboarding: true`,
и приложение показывает анкету вместо тренажёра, спрятав нижние вкладки.

Четыре шага: класс (7-11) -> математика -> предметы по выбору -> цель по баллам
(200-230, 230-260, больше 260). Правила — `core/profile_meta.py`:
- **русский язык не выбирается** и не хранится: его сдают все, он подставляется
  в `exam_list` при показе;
- математика обязательна и ровно одна: профильная или базовая;
- **число предметов по выбору**: с профильной математикой один или два, с базовой
  строго два. Выход за границы отклоняет сервер — клиента можно подменить.

В базе у пользователя: `grade`, `math_level`, `subjects` (только предметы по выбору),
`target_score`, `onboarded_at`. Смена уровня математики выбранное не сбрасывает — лимиты
пересекаются; обрезается только то, что не влезает в новый максимум.

правка из бота — переедут в таблицу, API менять не придётся.

Формат — подмножество markdown: `##`/`###`, списки `-` и `1.`, `> заметка`,

сторонние библиотеки тянуть неоткуда, внешние CDN в Telegram блокируются.

## Карточки (запоминание слов)
Вход — карточка на главной тренажёра. Колода одна: «Ударения», задание №4,
187 слов орфоэпического минимума. Карточка — слово без ударения ->
«Показать ударение» -> «Знаю» или «Не знаю».

Слова лежат в `content/cards/accents.txt`, ударная гласная пишется ЗАГЛАВНОЙ —
из неё получаются и вопрос, и ответ, и проверка строки. Строка, где ударение не
определяется однозначно, в колоду не попадает (то же правило, что у парсера
вариантов). «Ё» в вопросе показывается как «е»: догадаться, что там не «е», —
часть задания.

Прогресс — в таблице `card_progress` (ученик, колода, слово, этап, `due_at`),
а не в браузере: Telegram чистит хранилище WebView, а колода должна быть общей на
всех устройствах. Отметка пишется сразу после ответа — подходы часто бросают на
середине.

### Методика (переписана 02.09.2026, вторая редакция)
Всё держится на времени. Первая редакция считала повторы подходами — от неё
отказались, очередь росла быстрее, чем разбиралась.

**Два тренажёра, и они не пересекаются.**

- **Основной** — только новые слова, десять за подход, один проход без возвратов.
  Доступен всегда. «Знаю» закрывает слово сразу и навсегда, «Не знаю» кладёт его
  в список повтора и запускает таймер на 8 часов.
- **«Повторить»** — только слова с истёкшим таймером, до десяти за подход, первым
  тот, у кого срок истёк раньше. Открывается, когда созрело хотя бы **пять**
  слов; иначе кнопка не работает и показывается согласованный текст
  (`REPEAT_LOCKED` в `static/app.js`, менять только вместе с методикой).

**Путь слова:** новое -> ждёт 8 часов (`wait8`) -> ждёт 24 часа (`wait24`) ->
выучено (`learned`). Двигает слово только «Знаю» и только в «Повторить».

**Добивка внутри подхода «Повторить».** Сначала все слова подхода по разу, потом
те, где было «Не знаю», — ещё раз, и так кругами, пока по каждому не будет
«Знаю». Очередь добивки живёт на клиенте (`run.again` в `answerCard`), сервер
только записывает ответы.

**«Не знаю» в «Повторить» не меняет в базе ничего** — ни этапа, ни таймера. Слово
просто возвращается здесь и сейчас. Поэтому выход из приложения посреди подхода
безопасен: отвеченное «Знаю» уже записано, остальное осталось как было и придёт
в следующий раз.

**Отсчёт идёт от нажатия, которое перевело слово на новый этап** — то есть от
«Не знаю» в основном тренажёре и от «Знаю» в «Повторить».

**Новые слова кончились** — основной тренажёр пишет «Ты разобрал все возможные
слова». **Сброс стирает всё** — и выученные, и отложенные с таймерами.

**Кнопка «Повторить» нажимается всегда.** Не набралось пяти созревших — открывается
окно с согласованным текстом. Из-под кнопки этот текст убран намеренно: висящая
надпись рядом с серой кнопкой читалась как поломка.

### Два списка слов
- **«Слабые слова»** (`GET /cards/{deck}/weak`) — то, что на повторе. Порядок по
  мере попадания в список: строка `card_progress` заводится первым «Не знаю» и
  больше не пересоздаётся, поэтому её `id` и есть очерёдность.
- **«Выученные слова»** (`GET /cards/{deck}/learned`) — закрытое, свежее сверху.

Справа у каждого слова **кольцо из трёх сегментов** — путь 8 часов -> 24 часа ->
выучено. Заполнено столько, сколько этапов позади: один оранжевый, два жёлтых,
три зелёных с галочкой. Созревшее слово получает синюю плашку «Можно повторять!»,
а в центре кольца вместо времени «Го!».

Кольцо рисуется `conic-gradient` из `stageRing` в `static/app.js` — не картинкой
и не SVG: колец на экране до двух сотен.

Где что лежит: переходы — `crud.next_stage` и `crud.mark_card`, набор подхода и
цифры для экрана — `api/routers/cards.py`, экраны — блок «Карточки» в
`static/app.js`.

**Список слов не вычитан преподавателем** — за методику отвечает пользователь.

## Паронимы (задание №5)
Отдельный раздел, а не вторая колода карточек. Так решено сознательно: задания
разные, и общего кода у них нет — правка в паронимах не должна доставать до №4.
Своё всё: `core/paronyms.py`, таблица `paronym_progress`, `api/routers/paronyms.py`,
свой блок экранов в `static/app.js`. Цена известна и принята: менять что-то в обоих
сразу придётся дважды.

**Методика — копия №4 по договорённости.** Основной тренажёр: 10 новых групп, один
проход. «Знаю» закрывает группу сразу, «Не знаю» кладёт в слабые с таймером на
8 часов. «Повторить»: открывается от пяти созревших, до десяти за подход, добивка
до «Знаю» по каждой группе. Этапы `wait8` -> `wait24` -> `learned`, переходы —
`PARONYM_NEXT_STAGE` в `db/models.py`.

**Единица прогресса — вся группа.** Ответил про «эффектный / эффективный» — закрылись
оба слова разом. Ключ группы в базе — первое слово.

**Формат словника** `content/cards/paronyms.txt` — строка на группу, слова через `|`,
слово и значение через `=`:

```
эффективный = дающий нужный результат: эффективный метод | эффектный = производящий сильное впечатление: эффектный жест
```

Внутри значения ни `|`, ни `=` быть не должно — на этом держится разбор. Слов в
группе два или больше: в словнике есть тройки («дипломат / дипломант / дипломник»).

**Сейчас 70 групп: 59 пар и 11 троек.** Официальный словник больше. **Значения и
примеры не вычитаны преподавателем** — паронимы то место, где ошибка выглядит
правдоподобно и не бросается в глаза.

**Вход:** Тренажёр -> «Карточки» -> меню из трёх разделов: №4 Ударения, №5 Паронимы,
№22 Средства выразительности.

## Средства выразительности (задание №22)
Сделано 04.09.2026. **Это не карточки.** Программа проверяет ответ сама,
самопроверки «Знаю / Не знаю» здесь нет, а значит нет ни этапов, ни таймеров,
ни слабых с выученными.

- Экран: выражение, под ним четыре кнопки с названиями приёмов. Нажал — сразу
  зелёная или красная подсветка и кнопка «Дальше».
- **Один тренажёр на все 23 средства**, не три по группам. Отдельные тренажёры
  обсуждались и отброшены: название тренажёра само выдавало ответ (в фонетическом
  их всего два), а на экзамене группа не сообщается.
- **Четыре кнопки везде**, включая фонетические: обманки берутся со всего
  перечня, поэтому ассонансу есть с чем соседствовать.
- **Три обманки тянутся случайно** из 23 терминов. Гнёзда «похожих» приёмов
  проектировались и отброшены пользователем — см. «Что решено».
- Подход — 10 вопросов, в подходе не повторяются. Вопросы всегда случайные.
- Хранится только **точность по трём группам** («Лексические 70%»), показывается
  в самом тренажёре. На подбор вопросов не влияет и в общую статистику не входит:
  та про решённые задания.

**Вопросы берутся из базы, а не из файла.** У №22 в каждом варианте пять позиций
«выражение → приём», уже официальных и уже вычитанных источником. Восемь
вариантов дают **40 вопросов** (18 лексических, 17 синтаксических, 5
фонетических), и каждый новый залитый вариант добавляет пять сам, без правки
контента. Позиция, где термина нет в перечне 23, вопросом не становится — правило
то же, что у парсера: при неоднозначности не собираем.

**Покрыто 16 приёмов из 23.** Ни разу не были ответом: литота, вопросно-ответная
форма, градация, эпифора, риторическое восклицание, риторическое обращение,
бессоюзие. Они пока могут быть только обманками. Дописывать примеры — работа
преподавателя.

Где что лежит: перечень и сборка вопроса — `core/means.py`, ручки —
`api/routers/means.py` (состояние, подход, ответ, сброс), точность —
таблица `means_stats`, экраны — блок «Средства выразительности» в `static/app.js`.
Проверка ответа только на сервере: правильный приём не уходит на клиент заранее,
а подход нигде не хранится — вопрос адресуется парой «задание + позиция».

Черновик `content/means.txt` окончательно лишний: примеры берутся из базы.

## Что решено и не обсуждать заново
- Варианты ответа подписываются **цифрами** (1, 2, 3), не буквами — так в условиях ЕГЭ.
- **Ввод остаётся кнопочным.** Обсуждали переход на ручной ввод для всех видов, посмотрели
  вживую — решили оставить как есть.
- `DATABASE_URL` на Railway — **публичный** адрес, не внутренний (`problems.md` §2.4).
- Миграции только `ALTER ... IF NOT EXISTS`: `create_all` существующие таблицы не меняет.
  Новые таблицы (`card_progress`) `create_all` создаёт сам, миграция не нужна.
- JSON-колонки: `JSON().with_variant(JSONB(), "postgresql")` — тесты на SQLite, прод на Postgres.
- Проверять работу бота через `getUpdates` **нельзя**: вызов крадёт апдейт у запущенного
  сервера и даёт ложный отрицательный результат. Проверяет пользователь вручную.
- **Каждое задание — свой код, общего движка нет.** Обсуждали общий: у карточек
  уже была колонка «колода», и №5 добавлялся одной строкой. Решено иначе —
  паронимы получили свой разбор, свою таблицу, свои ручки и свои экраны.
  Довод пользователя: правка одного задания не должна доставать до другого,
  а править в двух местах его не смущает. Заново не переигрывать.
- **Обманки в №22 тянутся случайно из всех 23 терминов.** Предлагалась схема
  «гнёзд»: у каждого приёма три постоянных соседа, с которыми его путают
  (метафора — метонимия, олицетворение, сравнение), гнёзда взаимные и замкнутые,
  чтобы состав кнопок не выдавал ответ. Пользователь отказался: слишком сложно.
  Заново не предлагать.
- Индексы, `lazy="selectin"` и идемпотентные миграции уже на месте — заново не «оптимизировать».
- В `users` уже есть `plan` и `plan_until` — основа под подписки заложена.
- **Баллы (из `state.md`, официальная таблица):** все задания по 1 баллу, кроме №8 и №22
  — по 2. Максимум за вариант 28. У №8 и №22 есть частичный балл: ошибка на одной или
  двух позициях из пяти — 1 балл, три и больше — ноль. Частично верный ответ в
  статистике остаётся **неверным**, иначе точность врёт; балл при этом начисляется.
  Проверка и начисление идут парой — `scoring.score_answer`.
- **Тестового балла (100-балльной шкалы) нет.** Ученику показывается только первичный —
  сколько из 28, рядом точность в процентах. Таблицы перевода в коде нет и не заводим:
  без №27 она всё равно давала бы приближение. Колонка `sessions.test_score` осталась
  в базе и никому не мешает.

## Известные дефекты и незаконченное
1. **Шпаргалки написаны на 2 задания из 26.**
2. **Карточки и средства выразительности не покрыты тестами** — писались в режиме
   «проверяет пользователь». Переходы (`crud.next_stage`), набор подхода и разбор
   задания в вопросы (`means.pairs_from_task`) — чистая логика, тесты на них
   пишутся без базы.
3. **После двух повторов слово закрыто навсегда.** Выученное месяц назад не
   проверяется заново — третьего интервала (неделя, месяц) в методике нет.
   Место под него есть: `CARD_NEXT_STAGE` в `db/models.py` — таблица переходов,
   добавляется этап, ничего больше не меняется.
4. `/edit` в админ-боте разбирает задание старым шаблонным парсером (`parse_task`),
   который определяет вид по форме сообщения. У задания, залитого через `/upload`,
   правка условия может сменить вид — например, №21 станет «выбором варианта».
5. **Пароль базы на Railway засветился** открытым текстом в переписке. Адрес публичный.
6. `WEBAPP_URL` на Railway должен заканчиваться на `/app`, иначе редирект съедает `?v=`.

## История, чтобы не наступить снова
- В `import_variant` были два дефекта, оба починены: отпечаток не учитывал материал —
  8 заданий второго варианта приняло за уже залитые и потеряло; `--variant` собирал
  вариант только из созданных в этом запуске, поэтому повторный прогон молча не собирал.
- Дедуп когда-то шёл по отпечатку из текста: правка одного символа на сайте плодила
  копию задания. Теперь по `source_id`, отпечаток — запасной ключ.
- **`take_match` брал у позиции А-Д только строку с меткой**, а продолжение молча
  выбрасывал. В №22 позиция — почти всегда двустишие, и приём сидит во второй
  строке, поэтому ответы получались бессмысленными: «Людей неинтересных в мире
  нет.» → «сравнение». Испорчены были все девять собранных вариантов. Нашлось
  случайно, когда полезли в варианты за примерами для другой задачи. Мораль та же,
  что у истории с №13: строку, не легшую никуда, нельзя пропускать молча — теперь
  такие возвращаются четвёртым значением и печатаются заметкой при вычитке.
- **Чем кончилось с №22 (03.09.2026).** Перезаливка поверх не помогала: дедуп
  переиспользует задание по ID источника, а не переписывает, и вариант целиком
  отбивается как дубль по №26. Поэтому базу очистили `purge_db.py --yes` и залили
  восемь вариантов заново через `import_variant.py`. Перед заливкой разбор
  проверили тремя независимыми способами: аудит потерянных строк (было 46 на
  девяти файлах, стало 0), сверка №22 с пояснением источника (термин из прозы
  редакции против позиции, куда парсер поставил цифру — сошлось в 8 файлах из 9,
  девятый прозой и сверен вручную) и структурная проверка 234 заданий. **Если
  придётся чинить содержимое задания, которое уже в проде, помни: заливка его не
  трогает.** Либо чистка целиком, либо обновление строк на месте.
- `Ответ: 3, 5` разбирался как «верно 3 ИЛИ верно 5», и ученик, ответивший «35», получал
  «неверно», а написавший «3» — «верно». Ровно наоборот.
- Веса баллов были взяты из общей спецификации ЕГЭ, где нумерация другая: 4 балла
  доставались №26 с ответом из одной цифры, а соответствие на 5 позиций (№22) стоило 1.
- Прод чистили `scripts/purge_db.py --yes`: 2 варианта, 52 задания, 5 сессий, 130 ответов.
- `session_items.task_id` и `variant_items.task_id` стоят с `ondelete=RESTRICT`: база не
  даст удалить задание, на которое ссылается чей-то ответ. Удалять — только вместе с сессиями.

## Идеи, обсуждённые и отложенные
- **Объяснение при разборе ошибки — из своих шпаргалок, не с РЕШУ ЕГЭ.** Сначала
  предлагалось сохранять пояснение источника (оно и так проходит через парсер,
  оттуда берётся ответ, а текст выбрасывается). **Пользователь отказался:**
  задания из открытого банка — одно, а пояснение писал живой редактор сайта, это
  их труд. Решено вместо этого связать разбор ошибки со шпаргалкой по тому же
  номеру: ошибся в №4 — под ответом выжимка из чек-листа и кнопка «Как решать №4».
  Контент свой, переиспользуется на всех заданиях номера, и у шпаргалок появляется
  вторая жизнь — они приходят в тот момент, когда ученику правда интересно.
  Поле под своё пояснение к конкретному заданию — потом и адресно, по статистике
  ошибок, а не ко всем двумстам наугад.
- **«Работа над ошибками»** одной кнопкой: тренировка из номеров с худшей точностью.
  Статистика по номерам уже считается.
- **Серия дней** и напоминание из бота вечером. Единственное, ради чего нужен
  именно бот, а не сайт: приложение само ученику не напишет, а бот напишет.
- **Задание дня** — 5 заданий, одна попытка в сутки.
- Ещё колоды карточек: формы слова №7, исключения №9-14. Механику брать с №4/№5,
  но кодом не связывать — см. «Что решено».
- Отложено до аудитории: рейтинги, соревнования, достижения.

## Чего намеренно не делаем
- Проверка сочинения №27 — отдельный проект, нужна модель и критерии.
- Единый ручной ввод для всех видов — решено оставить кнопки.
- Рефакторинг работающего кода и аналитика, пока пользователь один.

## Как со мной работать
- **Тесты гоняет пользователь, не я.** После правки — перечитать написанное и
  проверить синтаксис, а не запускать `pytest` и сквозные сценарии. Проверка в
  Telegram тоже на пользователе.
- **Править файлы напрямую** через Write/Edit. Не гонять правки python-скриптами
  через bash-heredoc: `\n` внутри строки превращается в реальный перенос и ломает
  файл. Так уже трижды ломались `admin_bot.py` и тесты.
- Контента — минимум для проверки формата. Большой словарь до того, как пользователь
  увидел механику вживую, — работа впустую.
- Отвечать коротко: отчёт после задачи в несколько строк, а не страница. Пользователь
  на лимитах.
- Не проверять то, о чём не просили: если строка `include_router` видна на экране,
  выяснять список маршрутов не нужно.
- Перед крупным изменением — сначала план, потом код. «Черновик» в задании значит
  рабочий код без комментариев и документации.
- Не защищаться общими фразами: называть конкретный риск.
- Проверять утверждения по коду, а не по памяти. В этом проекте уже дважды оказывалось,
  что «надо оптимизировать» — давно сделано.
