# Train_gia — контекст проекта

Телеграм-бот с Mini App: тренажёр ЕГЭ по русскому языку.
ТЗ — `TZ.md`. Грабли прошлого проекта — `problems.md` (**читать перед работой**).

## Состояние на 31.08.2026
- 52 задания, 2 варианта, 1 пользователь. Тренировки по номеру **не запускаются**:
  `pick_random_tasks` берёт задания одного номера, а минимум в `TRAINING_COUNTS` — 6,
  сейчас по 2 на номер. Нужно 6 вариантов, тогда заработает само.
- 59 тестов, все зелёные.
- 6200 строк Python, 8500 строк фронта.

## Стек и архитектура
- Python 3.11, aiogram 3.29, FastAPI, SQLAlchemy 2.0 async + asyncpg, uvicorn, Docker
- Postgres 18 на Railway. Деплой автоматический: `git push` в `main`.
- `main.py` — один процесс: FastAPI + бот пользователя + админ-бот через `asyncio.gather`.
  `RUN_ADMIN_BOT_INLINE` выносит админ-бота в отдельный сервис (`admin.py`).
- Mini App: `static/`, проверка `initData` (HMAC-SHA256, ключ `WebAppData`) на каждом
  запросе, заголовок `X-Telegram-Init-Data`.
- **Рабочая папка должна быть `Train_gia`, а не `d:\VS`** — иначе этот файл не подхватится.

## Команды
```
python -m pytest -q                                       59 тестов

python scripts/import_variant.py Задания/2.json --dry-run проверка без базы

```

**Windows:** ставить `PYTHONIOENCODING=utf-8` перед `python`, иначе кириллица в выводе
рассыпается в мусор и кажется, что сломался код.

**Проверять, не трогая прод:** `DATABASE_URL="sqlite+aiosqlite:///tmp.db" python ...` —
переменные окружения перебивают `.env`. Локальный `.env` смотрит прямо в боевую базу.

## Виды заданий (`core/tasks_meta.py`)
| kind | что делает ученик |
|---|---|
| `choice` | выбирает пронумерованные варианты |
| `open` | вводит слово |
| `digits` | вводит цифры, порядок не важен |
| `match` | сопоставляет А-Д ↔ 1-9, порядок важен |

**Вид определяется номером задания, а не текстом** — таблица `KIND_BY_NUMBER`:
- `open` — 1, 5, 6, 7, 25
- `choice` — 2, 3, 4, 9-14, 16, 23, 24
- `digits` — 15, 17-21, 26
- `match` — 8, 22

Без таблицы возвращаются две ловушки: у №21 материал начинается с «1) 2) 3)» и выглядит
как варианты ответа, а формулировки №12 и №16 путают даже модели.

## Как задания попадают в базу
Пользователь копирует вариант с РЕШУ ЕГЭ **как есть**, сохраняет файлом (UTF-8), шлёт
в админ-бота командой `/upload`. Бот присылает разбор файлом на вычитку и ждёт
подтверждения кнопкой. Папка `Задания/` в `.gitignore`.

**Главное правило парсера: при любой неоднозначности задание не собирается**, а попадает
в `problems`, и файл не пишется. Прошлый парсер разбирал текст эвристиками, на №13 молча
потерял вариант ответа и сдвинул правильные — заметили не сразу.

## Ловушки исходников (все встречались вживую)
- **Мягкий перенос U+00AD** — по 8-9 тысяч на файл, невидим, рвёт слова внутри.
- **Латинская `A` вместо русской `А`** в столбце №22. Выглядит одинаково, столбец
  собирается из 4 позиций вместо 5, все ответы съезжают на букву.
- **Markdown-выгрузки**: шапка приходит как `↑ **Задание 2 № 45125 тип 2**`, «Пояснение.»
  как `**Пояснение.**`, часть строк дублируется подряд, пустая строка перед списком
  вариантов может пропасть, а маркер «Прочитайте текст» — потеряться совсем.
- **Источники ответа по приоритету**: `Ответ:` (все формы через «ИЛИ», «|», «;») →
  `Ответ в демоверсии:` / `Ответ редакции:` (объединяются) → `Правильный ответ:` (одна
  форма, парсер предупреждает). Ярлыки читаются только при отсутствии обычного `Ответ:`:
  под заданием бывает обсуждение, и реплика редакции подписана так же.
- Сайт печатает номер дважды («Задание 8 ... тип 8») — бесплатная проверка разбора.

## Соглашения, о которые легко споткнуться
- `correct` у `choice`: в JSON с единицы, в базе с нуля (`to_parsed` вычитает 1),
  на экране снова с единицы. Три системы отсчёта на одно поле.
- `correct` у `match`: везде с единицы, порядок важен — это позиции правого столбца
  в порядке букв А-Д.
- Правильный ответ не уходит на клиент, пока ученик не ответил. В полном варианте —
  до самого конца варианта, потому что до конца ответ можно менять.
- Запятая в строке ответа делит формы только если части без пробелов («145, 541»),
  иначе она часть самой фразы («не столько планы, сколько нас»).

## Что решено и не обсуждать заново
- Варианты ответа подписываются **цифрами** (1, 2, 3), не буквами — так в условиях ЕГЭ.
- **Ввод остаётся кнопочным.** Обсуждали переход на ручной ввод для всех видов, посмотрели
  вживую — решили оставить как есть.
- `DATABASE_URL` на Railway — **публичный** адрес, не внутренний (`problems.md` §2.4).
- Миграции только `ALTER ... IF NOT EXISTS`: `create_all` существующие таблицы не меняет.
- JSON-колонки: `JSON().with_variant(JSONB(), "postgresql")` — тесты на SQLite, прод на Postgres.
- Проверять работу бота через `getUpdates` **нельзя**: вызов крадёт апдейт у запущенного
  сервера и даёт ложный отрицательный результат. Проверяет пользователь вручную.
- Индексы, `lazy="selectin"` и идемпотентные миграции уже на месте — заново не «оптимизировать».
- В `users` уже есть `plan` и `plan_until` — основа под подписки заложена.

## Известные дефекты
1. **Названия тем сдвинуты** в словаре `TASKS`. Ученик видит чужой заголовок над заданием:
   №1, №2, №3, №22, №25, №26. С №4 по №21 сходится. Нужна свежая демоверсия ФИПИ.
2. **Веса заданий сдвинуты** так же. `TASK_MAX_POINTS[26] = 4`, но №26 — обычные цифры
   с ответом «9», а соответствие на 5 позиций это №22, и ему сейчас даётся 1 балл.
3. **Нет частичного балла за соответствие.** Ученик, угадавший 4 позиции из 5 в №8,
   получает 0 вместо 4. Правится в `check_answer` и `award_points`.
4. **`RAW_TO_TEST_SCORE` пуст** — тестовый балл линейное приближение, приложение честно
   об этом пишет. Нужна таблица Рособрнадзора. Без №27 потолок ниже, 100 недостижимо.
5. **ID источника выбрасывается.** Парсер вынимает `№ 38823` из шапки и не сохраняет.
   Дедуп идёт по длинному отпечатку из текста — ломается от любой правки.
6. **Пароль базы на Railway засветился** открытым текстом в переписке. Адрес публичный.
7. `WEBAPP_URL` на Railway должен заканчиваться на `/app`, иначе редирект съедает `?v=`.

## История, чтобы не наступить снова
- В `import_variant` были два дефекта, оба починены: отпечаток не учитывал материал —
  8 заданий второго варианта приняло за уже залитые и потеряло; `--variant` собирал
  вариант только из созданных в этом запуске, поэтому повторный прогон молча не собирал.
- Вариант 1 вместе с 26 заданиями и 3 сессиями удалён из прода по просьбе пользователя.
- `session_items.task_id` и `variant_items.task_id` стоят с `ondelete=RESTRICT`: база не
  даст удалить задание, на которое ссылается чей-то ответ. Удалять — только вместе с сессиями.

## План на ближайшие 3 дня (составлен пользователем)
**День 1 — приём и выдача.** Определиться, как принимать вариант в базу, чтобы всё
работало корректно. Перепроверить систему на 10 вариантах. Настроить админ-бота.

**День 2 — подсчёт и личный кабинет.** Правильный перевод баллов. Меню «Профиль»
и «Статистика». Сохранение статистики отдельно по каждому пользователю. Тренажёр.
Чек-листы и шпаргалки.

**День 3 — лендинг.** Работа над лендингом, продумать расширение функционала.

Приоритет пользователя, сказано прямо: **самое важное — чтобы задания корректно
попадали в базу и правильно выдавались ученику.** Остальное после.

## Чего намеренно не делаем
- Проверка сочинения №27 — отдельный проект, нужна модель и критерии.
- Единый ручной ввод для всех видов — решено оставить кнопки.
- Рефакторинг работающего кода и аналитика, пока пользователь один.
